# 统一搜索：一个框同时查视频和图片

图片库和视频库各自能搜，但回答的是同一句话的两半：`黑色衣服` 在视频里要找的是**哪一段**（时间点），在图片里要找的是**哪一张**（文件）。以前要么先去「搜索」页，要么先去「图片库」，取决于素材是视频还是照片。

侧边栏第二项 **统一搜索** 把两边合成一个输入框，一次请求返回两组结果。

## 1. 两条索引怎么合起来

界面层不拼装任何检索逻辑，真正的入口是 `src/services/unified_search.py` 的 `search()`：它跑两个引擎，返回一个字典。

| 侧 | 调用 | 为什么这样接 |
|----|------|--------------|
| 视频 | `execute_agent_search(AgentSearchRequest(...))` | Agent API 已经处理好查询解析、帧/片段模式、最低分策略、命中窗口扩展。另写一份必然与它漂移。 |
| 图片 | `image_index_service.search_by_query()` | 图片页用的就是它：属性 → 文件名/描述 → 向量三级路由，中文的三级分流逻辑不重复实现。 |

返回结构：

```python
{
  "query": "穿得花哨的人",
  "scope": "all",              # all / video / image
  "videos": [...],             # path / 时间码 / 分数 / 匹配文字
  "images": [...],             # 与图片页同一份 hit 字典
  "video_error": "",           # 索引没建好时是 "index_not_ready"
  "image_error": "",
  "image_channel": "attribute",# attribute / literal / vector
  "image_attributes": "穿搭风格=花哨",
  "elapsed_ms": 803,
}
```

**两侧各自成败**。视频索引没建好，图片照常返回；图片库是空的，视频也照常返回。任一侧抛异常只写进自己的 `*_error`，另一侧的列表不受影响——半张结果比全空有用。`IndexNotReadyError` 会被翻译成 `index_not_ready` 标记，页面据此说"先去「视频库」建库"，而不是把英文异常原样贴出来。

## 2. 为什么不做跨模态混排

两边的分数**不在同一把尺子上**：视频是 CLIP 片段相似度（0.30–0.45 常见），图片属性检索是 19 条提示词的组内 softmax（0.95 以上很常见）。把它们排进一个列表，等于让图片永远压住视频，而且这个"优势"与相关度无关。

所以结果是**分组**的：上面视频条，下面图片墙，各自有计数。状态行说清两侧各多少条、用了多久、命中了哪些属性词。

## 3. 界面

```
┌ 统一搜索 ────────────────────────────────────────────┐
│ 搜索                                                  │
│ [全部 ▾] [描述画面，或写属性词……            ] [搜索]  │
│ 视频 12 条 · 图片 48 张 · 用时 0.8 s · 属性：穿搭风格=花哨 │
├ 视频片段（12 条）───────────────────────────────────┤
│ [16:9 帧] [16:9 帧] [16:9 帧] …  ← 横向滚动           │
│  文件名     文件名                                    │
│  00:12 · 0.31                                        │
├ 图片（48 张）───────────────────────────────────────┤
│ 缩略图墙，与图片库同一个网格模型与委托                  │
└──────────────────────────────────────────────────────┘
```

- **范围**：`全部` 两侧都跑；`只搜视频` / `只搜图片` 直接跳过另一侧，省掉一次索引查询（实测图片侧 16 ms，视频侧 0.8 s）。
- **双击视频**：切到「搜索」页，在固定播放器里播这一段。不在这里另起播放器——那会变成第二个 VLC 实例、第二套进度条，且与搜索页的预览状态不一致。
- **双击图片**：用系统看图打开。跳进图片库需要按 id 定位并滚动到那一格，目前图片页没有这个入口，先给最直接的路径。
- 回车即搜，输入框自带清空按钮。

## 4. 实测

1262 张素材 + 现有视频库，单次请求：

| 场景 | 耗时 |
|------|------|
| 进程内首次（CLIP 引擎加载） | 15.0 s |
| `黑色衣服`（视频 + 属性） | 0.85 s |
| `穿得花哨的人`（视频 + 属性） | 0.70 s |
| `浅色衣服`（视频 + 属性） | 1.29 s |
| `a man in a suit`（视频 + 图片 CLIP 文本塔） | 1.33 s |
| 只搜图片（属性） | 16 ms |
| 只搜视频 | 0.8 s |

视频侧是索引查询，0.7–1.3 s 基本是它自己的开销；图片属性检索 13–19 ms，英文查询要过 CLIP 文本塔，约 326 ms。冷启动那 15 秒只出现一次，之后进程内都是上表的数字。

## 5. 已知取舍

- **视频命中是片段级**，不是帧级：`start_sec`/`end_sec` 是命中的窗口，播放器会从这个窗口开始播，不保证停在那一帧。
- **图片命中是文件级**：告诉你哪张照片里有"穿花哨的人"，不做区域定位、不画框。
- **不做二次精排**：一个框只跑一次各引擎的默认策略，不追加"用 VLM 描述再排一遍"。那会把 0.8 秒变成十几秒，而用户按范围筛选已经能表达意图。
- **缩略图只预取前 120 格**：加载器的在途上限是 8，超出的请求会被丢弃并等下一次重绘。结果页可能静止不动，所以页面自己用 200 ms 的定时器补页；超过 120 格的部分交给滚动时的重绘，避免给没人看的格子解码。

## 6. 代码地图

| 文件 | 作用 |
|------|------|
| `src/services/unified_search.py` | 双侧检索 + 结果整形 + 分侧错误。纯数据，无 Qt。 |
| `ui/widgets/unified_search_page.py` | 页面：搜索卡、视频条（模型 + 委托）、图片墙（复用图片库的网格）、缩略图泵。 |
| `ui/windows/gui.py` | 注册导航页（`search` 之后）、页面栈、按钮点击。 |
| `ui/windows/gui_preview.py` | `_on_unified_video_activated` → 切页 + `handle_play`。 |
| `ui/widgets/image_library_page.py` | 网格模型/委托被复用；新增 `has_thumb()` 与缩略图泵。 |
| `tests/test_unified_search.py` | 19 个用例：范围归一、命中整形、分侧失败、渠道标注、页面填充、语言切换、补页。 |

一个实现细节值得记下来：视频条最初用 `QListWidget` 的图标模式 + `setGridSize()`，Qt 6 下 `gridSize` 不生效（单元格按文字高度算成 30 px），缩略图被裁掉、标题看不见。改成 `QAbstractListModel` + 委托、由 `sizeHint()` 决定 196×160 才正常——图片墙本来就是这套做法，两个区域现在一致。
