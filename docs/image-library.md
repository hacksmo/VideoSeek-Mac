# 图片库：理解、索引与检索

给「照片 / 截图 / 素材图」建语义索引，并且**不只看图上的文字**——每张图会得到一句描述、一组结构化人物信息、一组标签，全部可检索。

与视频库的关系：**完全独立**。图片走自己的 `image_assets` 表，视频的 `frames` / `chunks` / `dialogue_segments` 一个字节都不动。

---

## 1. 一张图会存下什么

| 字段 | 内容 | 来源 |
|------|------|------|
| `vector` | 512 维 CLIP 向量（跟随当前模型 profile） | 本地 ONNX，CPU |
| `caption` | 一句话描述整张图 | VLM |
| `people_json` | 结构化人物数组 | VLM |
| `tags_json` | ≤12 个短标签（场景 / 物品 / 风格 / 颜色） | VLM |
| `image_path` / `rel_path` / `library_root` | 定位信息 | 文件系统 |
| `width` / `height` / `bytes` / `mtime` | 增量索引依据 | 文件系统 |
| `describer` | 谁生成的描述（`vlm:<model>` / `vlm-error:<type>` / `clip-only`） | 内部 |

`people[]` 每条的结构：

```json
{
  "count": 1,
  "gender": "女",
  "age": "青年",
  "clothing": "红色连衣裙",
  "action": "站在窗边看手机",
  "position": "画面左侧",
  "features": "长发，戴细框眼镜"
}
```

这就是「人物描述」的落点。它**不放进 `tags`**——`src/services/understanding_tags.py` 里的 `_GENERIC_FILLERS`
会把 `男人 / 女人 / person / people` 当成 C 级填充词丢掉（视频镜头打标签这么做是对的），
所以人物信息走独立字段，检索时才不会被过滤掉。

## 2. 图形界面（应用内「图片库」页签）

侧边栏 **图片库**，位置在「视频库」下面。整页分三块：

| 区域 | 内容 |
|------|------|
| 照片目录 | 添加 / 移除 / 打开文件夹，列出已登记目录 |
| 索引 | 重新扫描 → 开始索引 → 停止；勾选「同时生成描述」「强制重算」；进度条带剩余时间 |
| 检索 | 语义 / 关键词 / 以图搜图、人数下限、结果数、浏览全部；左侧缩略图网格，右侧详情 |

一次完整的流程：

1. **添加文件夹**（或把文件夹拖进页面）→ 自动扫描，提示「发现 N 张照片」
2. 想要人物描述就勾选「同时生成描述」。VLM 没启动时这个勾选框是灰的，悬停可看原因
3. **开始索引**。超过 1500 张会先确认；跑起来后显示 `已完成/总数 · 文件名 · 剩余约 X`，随时可停
4. 索引结束自动切回「浏览全部」，最近修改的排在最前
5. 点任意缩略图，右侧出现大图、描述、人物、标签、尺寸与路径

交互细节：

- 把**文件夹**拖进页面 = 添加目录；把**一张图片**拖进页面 = 以图搜图
- 双击缩略图用系统看图应用打开；详情区也有「打开图片」「在访达中显示」
- 「人数」筛选在语义和关键词模式下都会生效（语义结果按 `people_count` 后置过滤）

### 缩略图为什么要单独缓存

一张 4000×3000 的照片解码后约 36 MB，耗时上百毫秒。网格若逐格解原图，滚动必然卡死。
所以首次需要时才在后台线程解一次，并落盘复用：

```
~/.videoseek/cache/image_thumbs/<image_id>_256.jpg    # 网格
~/.videoseek/cache/image_thumbs/<image_id>_1024.jpg   # 右侧大图
```

`image_id` 是文件内容哈希，图片变了 id 就变、缓存自动失效，不需要手动清。
删掉这个目录是安全的，只会重新生成。网格本身是虚拟化的（`QListView` + 自绘 delegate），
只画可见单元格，几万张也能滚。

### 中文检索先看模型

搜索框下方会按需提示当前模型的文本语言：

- **OpenAI CLIP**（默认）：英文训练，中文描述命中率明显偏低
- **Chinese CLIP / SigLIP2**：中英文都可以

中文搜不到**不代表索引坏了**。换模型：设置 → 模型 → 选 Chinese CLIP 或 SigLIP2，
回图片库「重新扫描 → 开始索引」重建向量（换模型会重建 `image_assets` 表，图片是派生数据，无损失）。

## 3. 三步用起来

```bash
cd ~/Desktop/VideoSeek
V=~/.videoseek-venv/bin/python

$V scripts/image_index.py add ~/Pictures/travel     # 登记目录（可多次）
$V scripts/image_index.py scan                      # 看有多少张待索引
$V scripts/image_index.py index                     # 编码 + 描述
$V scripts/image_index.py status                    # 看总量 / 维度 / VLM 是否就绪
```

`index` 的输出是结构化统计：

```json
{
  "scanned": 128, "added": 128, "updated": 0, "skipped": 0,
  "failed": 0, "described": 128, "describe_failed": 0,
  "describe_enabled": true, "describe_reason": ""
}
```

增量规则：文件 `mtime` 没变、且已有非空 `caption` 的行直接跳过。想强制重算用 `--force`。
只想算向量、不调模型用 `--no-describe`（几百张图几分钟内完成，之后可随时补描述）。

## 4. 三种检索

```bash
# 语义（CLIP 文本向量）—— 描述性查询
$V scripts/image_index.py search "穿红裙的女人站在窗边" --top-k 10

# 关键词（caption / people / tags 子串）—— 确定词
$V scripts/image_index.py search "红裙" --mode keyword
$V scripts/image_index.py search "青年" --mode keyword --min-people 1 --max-people 2

# 以图搜图（CLIP 图片向量）
$V scripts/image_index.py search --mode image --image ~/Pictures/q.jpg
```

| 模式 | 适合 | 局限 |
|------|------|------|
| `text` | "海边日落"、"会议室白板" 这类整体语义；中文属性词（浅色衣服、胖子、花哨） | CLIP 对人数、精确颜色名不敏感；中文需靠属性筛选或文件名兜底 |
| `keyword` | 已知确切片语："红裙"、"眼镜"、"2人" | 需要先有描述；子串匹配，不做同义词扩展 |
| `image` | 找同款构图 / 同一场景 | 只比整体视觉，不比文字 |

实测：以图搜图时查询图自身的得分是 `1.000` 且排第一，属正常的自匹配基线。

### 中文查询怎么走

默认模型 `openai-clip/vit-base-patch32` 的**文本塔只认英文**。中文查询送进去基本是噪声——在 1262 张素材库上实测：

| 查询 | 直连 CLIP 的结果 |
|------|------------------|
| `红酒瓶` | 搞笑表情包 |
| `穿西装的男人` | 「老公在家」穿搭图 |
| `南京夫子庙夜景` | 羊羔绒面料科普图 |
| `a bottle of red wine` | 奔富红酒（准确） |

所以 `search`（界面「语义检索」和 CLI 默认模式）现在按查询语言分流，中文查询走三级：

```
含汉字 ──┬─> 属性筛选（颜色 / 体型 / 风格）   ← 命中即返回
         ├─> 字面扫描（文件名 / caption / tags / people）
         └─> CLIP 向量（前两级都空时才用，界面会标注"可能不相关"）
纯英文 ──> 直接走 CLIP 向量
```

字面扫描不用分词器，按停用字切开每段连续汉字，再展开 2–4 字滑窗：

```
穿西装的男人 -> ["穿西装", "穿西", "西装", "男人"]
红酒瓶       -> ["红酒瓶", "红酒", "酒瓶"]
```

排序按**命中最长片段的长度**主导，其余命中片段加权。所以「肌肉男穿西装」排在只有「西装」二字的图前面。同一批查询在分流后的结果：

| 查询 | 分流后 Top 1 |
|------|--------------|
| `穿西装的男人` | 肌肉男穿西装 |
| `老钱风穿搭` | 170+ 秋冬老钱风穿搭 |
| `红酒瓶` | 奔富 407 汇立红酒文化 |

**文字分流只解决"找得到文件"，不解决"看得懂画面"**：它依赖文件名/描述里有对应中文词。搜「夫子庙」而文件名里没这三个字，照样召回不到。

### 属性检索：不装模型也能按画面筛

真实使用中大量的查询是**属性型**的，和文件名完全无关：

```
浅色衣服   黑色衣服   肚子胖的人   个子矮的人   穿得比较花哨的人
```

这些词在任何文件名里都不会出现，中文 CLIP 也救不了——问题不在语言，而在任务：它要的是
"这张图里的人衣服是不是浅色"，属于细粒度视觉属性。

做法是把属性变成一组**英文提示词**，取它们的均值向量当作零样本分类器的权重，与索引里
已存的 CLIP 图片向量做点积，再在组内做 softmax。整段不写索引、不调 VLM、不下载模型：

```
提示词 "a person wearing light coloured clothes such as beige, cream..." 
      └─ 文本编码 ─> 单位向量 ─┐
                                ├─ 点积 → 组内 softmax → 每张图的置信度
已索引图片向量（512 维，归一化）─┘
```

在 1262 张素材库上逐组目检 Top 12 的实际准确率：

| 属性 | 组 | 目检命中 | 说明 |
|------|----|----------|------|
| 黑色衣服 | 衣服颜色 | 12/12 | 最稳 |
| 浅色衣服 | 衣服颜色 | 10/12 | 错的两张是面料特写 / 服装道具图 |
| 肚子胖的人 | 体型 | 9/12 | 会漏掉只拍上半身、看不出腹部的图 |
| 穿得花哨的人 | 穿搭风格 | 10/12 | 满 logo、撞色、印花都能抓到 |
| 个子矮的人 | 身高 | — | **不可靠**，CLIP 没有身高概念，结果随机 |

支持的词（写在一起也可以，多个属性相乘排序）：

| 组 | 可用的查询词 | 可选值 |
|----|--------------|--------|
| 衣服颜色 | 浅色 / 淡色 / 米色 / 白色 / 黑色 / 深色 / 暗色 / 彩色 / 亮色 / 鲜艳 / 印花 / 花纹 / 图案 / 格子 / 条纹 | 黑色、白色、浅色、深色、彩色、印花 |
| 体型 | 胖 / 微胖 / 肚子 / 大肚 / 啤酒肚 / 圆润 / 瘦 / 苗条 | 偏胖、匀称、偏瘦 |
| 穿搭风格 | 花哨 / 花里胡哨 / 浮夸 / 张扬 / 素净 / 简约 / 纯色 / 西装 / 正装 / 商务 / 休闲 / 街头 / 运动 | 花哨、素净、正装、休闲 |
| 身高 | 矮 / 个子不高 / 小个子 / 高个 / 高挑 | 偏矮、中等、偏高（**仅参考**） |

```bash
$V scripts/image_index.py search "浅色衣服" --top-k 30
$V scripts/image_index.py search "穿黑色衣服的胖子" --top-k 30   # 两个属性相乘
```

几处刻意的取舍：

- **"浅色"同时接受"白色"**——中文语境里白衬衫就是浅色衣服，拆开反而漏。
- **不拍人的图会被降权而不是丢弃**。属性分类器会误判约五分之一的面料/道具图为"有人"，
  硬过滤会连带丢掉真正的人物图，所以按 0.35 倍降权处理。
- **否定词会改判而不是命中**：`不花哨的简约穿搭` 走"素净"；`不瘦的人` 直接放弃体型约束。
  `个子不高` 是特例——这里的"不"属于词本身，按"偏矮"处理。
- **身高组保留但标注不可靠**。遮挡、镜头焦距、是否全身都会影响判断，单张图上的身高
  天生不可测；留着的价值是给全身照排序，而不是当事实。
- 首次查询要编码 19 条提示词（约 2.5 秒，结果缓存到
  `~/.videoseek/cache/attribute_prompts/`），之后每次 3 毫秒。

```bash
rm -rf ~/.videoseek/cache/attribute_prompts   # 换模型后清缓存
```

**属性 ≠ 语义**：它能回答"是不是浅色"，不能回答"这件衣服是什么风格"。要精确到
"穿红裙子的小孩在沙滩上"，仍然需要 VLM 描述——见第 5 节。

## 5. 人物描述从哪来

复用你已有的 VLM 配置，**不新增任何依赖、不下载新模型**：

**设置 → 理解 → 模型服务 → VLM**

| 方式 | base_url 示例 | 说明 |
|------|---------------|------|
| Ollama | `http://127.0.0.1:11434/v1` | 本仓库默认搭配，命令行安装、系统服务常驻 |
| LM Studio + Qwen3-VL | `http://127.0.0.1:1234/v1` | 图形界面，适合想手动换模型的人 |
| 云端 OpenAI 兼容 | 按服务商填 | 速度快、按量计费 |

### macOS 上装 Ollama

```bash
brew install ollama          # 装完会得到 /opt/homebrew/bin/ollama
ollama pull qwen3-vl:4b      # 3.1 GB
./start-ollama.command       # 双击亦可：拉起服务并列出已装模型
```

`start-ollama.command` 会先尝试注册登录项（重启后自动恢复），被系统拒绝时退回普通
后台进程，两种方式对 VideoSeek 没有区别——它只认 `127.0.0.1:11434/v1` 这个地址。

选型上：`4b` 是速度和够用的平衡点，单张约 2–4 秒；`8b` 描述更细但要多花一倍时间。
描述是一次性写入、可反复重跑的，先用小模型把所有图铺一遍，之后换成 `8b` 重跑即可：

```bash
./start-ollama.command                  # 换模型前先确认服务在
ollama pull qwen3-vl:8b
$V scripts/image_index.py index         # 自动发现模型变了，只重写描述
```

不用 `--force`：`describer` 里记着写描述的是哪个模型，和当前配置不一致就会重跑，
向量不重算。`--force` 是"连向量一起重建"，只在换**检索**模型时才需要。

提示词要求模型输出严格 JSON，并内置三条边界：
1. **不推测**姓名、身份、职业、情绪、关系；
2. **不评价美丑**、不评判身材好坏，`build` 只按可见轮廓中性归类；
3. 看不清的字段写「不确定」，不许编造。

这三条是刻意的：人物描述很容易滑向"识别这个人是谁"，那是另一件事（也涉及合规），本功能只做
**画面可见属性的描述**，不做人脸识别、不做身份归属。

每条人物记录除 `gender / age / clothing / action / position / features` 外，还带两个专供检索
的字段：

| 字段 | 取值 | 为什么单独开 |
|------|------|--------------|
| `build` | 偏胖 / 微胖 / 匀称 / 偏瘦 / 不确定 | 属性检索能筛，但 CLIP 只看整体；VLM 会结合轮廓给出更稳的判断 |
| `style` | 花哨 / 素净 / 正装 / 休闲 / 运动 / 不确定 | 「花哨」不是颜色，是配饰、图案、撞色的综合，文字描述比向量可靠 |

这两个字段会拼进 `people_json` 的可检索文本，所以 `search --mode keyword "偏胖"` 也能用。
拍照只到胸像、或穿宽松外套看不出轮廓时，模型按要求写「不确定」，不做猜测。

模型不听话、返回散文时不会失败：整段文字降级为 `caption`，`people` 为空，`parse_ok=False`。
向量照常写入，语义检索仍可用。

还有第三种情况：**JSON 被 token 上限截断**。人多、字段多的图很容易超预算，早期版本会把整段
残缺 JSON 当散文写进 `caption`，于是这张图既没有人物、也没有标签。现在两道保险：

- 解析器会退到最后一个分隔符，丢掉尾部半截键值，再把没闭合的括号补上；
  凡是切在字符串中间的方案都会跳过——那样补上的引号等于替模型编了一个值。
- 真解析不出来时，`describer` 记成 `vlm:模型名:unparsed`。`index` 会**自动重跑**这些行，
  不需要 `--force`。否则这类行看起来"已完成"（它有 caption），mtime 校验会一直跳过它。

全库跑完后从头到尾校验一遍，是最容易看出模型有没有跑偏的方式。1262 张零失败时是这样的：

```text
行数 1262 · JSON 解析成功 1262 (100.0%) · 有人物 1042 · 无人 220
build: 匀称 988 · 不确定 190 · 偏胖 109 · 偏瘦 36 · 微胖 3
style: 休闲 690 · 正装 557 · 素净 22 · 不确定 21 · 运动 17 · 花哨 13
```

解析率应当接近 100%；低于 90% 就先怀疑服务连通性或 token 预算。还有一个值得看的细节：
`style` 里混进了 `工装 3 / 时尚 1 / 校服 1 / 古装 1` 共 6 条**词表外取值**——模型偶尔自创说法，
这是本地小模型的固有现象。**不影响属性检索**（那条路径是向量判的，不读 `style`），
只是 `--mode keyword` 搜不到这几张。要收紧可以在提示词里写"只能从给定词里选"，
代价是模型更容易退成「不确定」。

两个 sanity check，跑完全量顺手做一次：

- `search --mode keyword "偏胖"` 应接近上面的 build 统计（这里 **100 行 vs 109 条人物记录**，
  差 9 是因为同一张图里有 2 个偏胖人物，行去重了）。差得远说明 `build` 没进可检索文本。
- `search "偏胖" --min-people 1` 的结果数应当等于"有人物"的行数（**1042**）——
  说明人数筛选和描述对齐了。注意 `--min-people` 是**属性检索的过滤器**，不是减 top_k：
  不加限制时属性检索会对全库 1262 行都打分。

服务没启动时也有明确降级：

```
VLM 就绪 : 否 已配置 http://127.0.0.1:1234/v1，但服务127.0.0.1:1234 不可达（ConnectionRefusedError）
```

此时 `index` 自动切到"只算向量"，并在 `describe_reason` 里说明原因，不会把每张图都记成失败。

## 6. 性能

Apple Silicon（M5 / 16 GB）、Metal 加速：

| 阶段 | 量级 |
|------|------|
| CLIP 编码 | 每张 50–150 ms |
| VLM 描述（Ollama qwen3-vl:4b，896 px 上传） | 每张 2–13 s；1262 张实跑平均 12 s/张，输出长度是主因 |
| 缩略图（首次） | 2400 万像素 JPEG 约 25 ms，HEIC 约 30 ms；之后直接读缓存 |
| 关键词检索 | 全表扫描，万级图片仍在百毫秒内 |
| 向量检索 | 毫秒级 |
| 浏览 5000 行 | 约 30 ms（不取 512 维向量，只读元数据列） |

两处影响最大、也最容易被忽略的调优：

**上传边长**。默认 1920 px，对"认衣服颜色、体型、风格"是过量信息。同一批图对比：

| 上传边长 | 每张耗时 | 描述效果 |
|----------|----------|----------|
| 1920 px | 5.9 s | 基准 |
| 896 px | 3.9 s | 肉眼看不出差别 |

改配置即可（`~/.videoseek/config.json` → `understanding.remote_vlm.upload_max_long_edge`），
`0` 表示用内置默认值。整批大约快三分之一。

**并发**。`--concurrency` 默认 2，但 Ollama 的 `OLLAMA_NUM_PARALLEL` 默认是 1，
两个请求只会在服务端排队，同一小批图实测反而更慢（8.6 s/张 → 串行 6.5 s/张）。
单机单模型就写 `--concurrency 1`。

缩略图不是"解原图再缩"：`cv2.imdecode` 支持 `IMREAD_REDUCED_*`，按目标尺寸边解边缩，
2400 万像素的照片从 600 ms 降到 25 ms 左右。这一步对"几万张照片"的体感影响最大。

1262 张真实图库完整跑完的实测：**22:27 起，02:49 结束，历时 4.4 小时，
1262 张全部有描述、零失败、JSON 解析率 100%，平均 12.4 s/张**。只算向量是 2 分 43 秒。
比上面那组小样本慢一倍，因为人像库里近景大图、多人合影多，输出 JSON 长。
扫描到 1268 个文件、入库 1262 行，差的 6 个是内容哈希相同的重复图。

中途可以随时 `Ctrl-C`，再跑 `index` 会跳过已有描述的图，从断点继续 ——
重跑一次看 `skipped` 是否等于文件数，就知道有没有遗漏。

## 7. 日常维护

### 往文件夹里加照片之后

**没有文件监听**——加完照片要自己跑一次索引：页面上点「开始索引」，或者命令行 `$V scripts/image_index.py index`。
不跑就搜不到，因为检索只查已入库的行。

索引是增量的，判定条件只有三条，任一成立才重做：

| 情况 | 会重做什么 | 不会重做什么 |
|------|-----------|-------------|
| 新文件（库里没有这行内容哈希） | 编码向量 + 跑一次 VLM | — |
| 同名文件被覆盖（mtime 变了） | 编码向量 + 重跑 VLM，旧描述被替换 | 其它照片一律跳过 |
| 同一张图换了个目录 | 什么都不做（`image_id` 是内容哈希，已经算过） | — |

没动过的照片**既不重算向量，也不调模型，也不重新读盘**——这是"每天跑一次 index"能成立的前提。
路径和 mtime 都对得上的行直接用已存的 `image_id`，跳过内容哈希：1262 张的外置硬盘库实测，
1261 张走这条快路，比对 3 ms；改造前每张都要完整读一遍算 SHA-1，合计 23 秒。
1262 张里加 20 张，实际工作就是 20 张（外加约 1 秒的元数据预载）。

三种会被自动补跑的行，不用 `--force`：

- **没描述过的**（`describer=clip-only`，当时 VLM 没启动）→ 只补描述；
- **描述解析失败的**（`describer=...:unparsed`）→ 换更宽松的解析后自动重试；
- **换了 VLM 模型的**（`describer` 里记着模型名，与当前配置不一致）→ 重写描述，向量不动。

最后一条是刻意做的：以前换模型只能 `--force`，而 `--force` 会连向量一起重算——为了改文字付一遍编码的钱。

删除了/移动了的照片，索引里的旧记录要清（`prune`）：

照片被移动或删除后，索引里的旧记录会留下打不开的空白格子。两种清理方式等价：

- 页面里点 **清理失效**（有进度、会告诉你清掉几条）
- 命令行：

```bash
$V scripts/image_index.py prune --dry-run   # 看有多少条记录的文件已不存在
$V scripts/image_index.py prune             # 删掉这些记录
$V scripts/image_index.py remove <folder>   # 取消登记（不删已索引行）
```

**外置硬盘没挂载时不会误删**：已登记目录本身不可达，说明是硬盘拔了而不是照片没了，这些行会被跳过，页面提示「有 N 条记录所在目录当前不可用」。

### 检索几乎不花算力

VLM 只在**建索引时**用一次，搜索路径完全不碰它：

| 查询类型 | 实测耗时（1262 张） | 用到什么 |
|----------|-------------------|---------|
| 属性（浅色衣服、肚子胖的人） | 3–5 ms | 已存 CLIP 向量 × 内存里的提示词向量；提示词只在首次编码一次（2.5 s，之后走缓存） |
| 属性 + 人数筛选 | 首次 930 ms，之后 7 ms | 首次要把 1262 行的向量矩阵读进内存，之后复用它 |
| 关键词（偏胖、红裙） | 230 ms | 全表扫描 `caption` / `people_json` / 文件名 |
| 英文语义（a man in a red suit） | 160 ms | 本地 ONNX 文本塔编码 + 向量检索 |
| 中文语义兜底 | 160 ms | 同上（属性、字面都没命中时才走） |

所以"搜一次要等模型算半天"是不存在的：属性检索 3–5 毫秒，关键词四分之一秒。
上面的数字是在描述全量跑完之后测的，行数和描述长度都已到底，以后只会更快。

只有**导入新照片**那一次会花 12 秒/张。

注意事项：

- **向量矩阵缓存**：键是 Lance 目录的 mtime，重跑 `index` 会自动失效——这正是为了不出现"加了新图却搜不到"。
- **换检索模型**：向量维度变了会自动重建 `image_assets` 表并提示重新索引（图片是派生数据，重建无损失）。
- **删索引**：直接删 `image_assets` 表即可，视频索引不受影响。
- **去重**：`image_id` 是文件内容的 SHA-1 前 32 位，同一张图放在两个目录只会索引一次。

## 8. 边界（本阶段不做）

| 不做 | 原因 |
|------|------|
| 多选批量操作（批量重描述、批量移除） | 页面是逐张查看；批量管理仍走 CLI |
| 视频与图片在同一个搜索框里混排 | 已做成单独页面（侧边栏「统一搜索」，见 `docs/unified-search.md`）；这里是**分组显示**，不混排打分 |
| 人脸识别 / 人物聚类 / 身份归属 | 合规风险，且与"描述画面"是两件事 |
| 中文语义理解（不靠文件名） | 需要换模型：设置 → 模型里切 `chinese_clip_onnx` 或 `siglip2_onnx`。两者的模型文件不在默认模型包里，得先导入；切换后**必须重算索引**（向量空间不同） |
| 一张图多个区域分别描述 | 单图单向量；区域级需要检测框 + 多向量 |
| 本地 VLM（ONNX） | 现有链路全是 OpenAI 兼容 HTTP，接本地 ONNX VLM 是新工程 |
